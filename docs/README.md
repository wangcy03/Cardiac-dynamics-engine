# 文档地图与维护职责

维护日期：2026-10-16。原则：一类问题只设一个权威入口；事实、计划、方程、证据分开。
保留现有文件与 B00–B09 编号，不搬动 `reference/`、`legacy/` 或历史报告。

## 1. 按问题找文档

| 要回答的问题 | 权威维护位置 | 不应该放在这里的内容 |
|---|---|---|
| 如何安装、快速运行和找到资料？ | 根 [README](../README.md) | 逐票状态、复制的结果数字表 |
| Codex 怎样接手和选择任务？ | [START_HERE](../START_HERE.md) | 第二份排期、重复多份历史启动语 |
| 做到哪里才算达到目标？ | [ROADMAP](../ROADMAP.md) | 每次运行的计数、耗时、逐票状态 |

| 参数、数据及适用域缺口？ | [PARAMETERS](PARAMETERS.md)、[DATA_GAPS](DATA_GAPS.md)、[SOURCES](SOURCES.md) | 编造的患者参数/默认零延迟 |
| 原理与证据怎样同步？ | [PRINCIPLES_MAINTENANCE](PRINCIPLES_MAINTENANCE.md) | 把证据刷新当成重新求解 |

| 真实输出和不可变历史？ | `artifacts/`、冻结运行目录 | 手改输出让测试通过 |

`DELIVERY_NOTES.md` 是交付摘要，`REVIEW.md` 与 `handoff/` 是既有复审/交接上下文；
它们不取代当前计划。旧报告继续保留，时间范围必须明确。

## 2. 读取顺序

新会话：`AGENTS.md → START_HERE.md → STATUS.md → ROADMAP.md → NEXT_ITERATION.md → BACKLOG.md → 选中票 SPEC`。
仅修改一个已分配任务时，可直接读当前计划、该 SPEC 和其引用，不必把所有历史 HTML 重新读一遍。
需要基础需求时回 r1/r0，需要数学解释时回原理文档，需要事实时回原始证据。

## 3. 状态只有一个维护源

- BACKLOG 维护逐票工作状态与报告指针；当前计划只排序，不复制每项状态。
- STATUS 汇总阶段能力和边界，不再维护第二份逐票看板。
- ROADMAP 定义长期阶段，不随每次测试改写。
- SPEC 定义目标和验收；执行结果另写报告，不在目标中悄悄调整容差。
- 不另建手工同步的 JSON 任务状态库；以后接 GitHub Issues 时，先明确哪个是状态主源，另一个只做索引/自动镜像。
- 现有 `requirements_trace_r2.json` 是需求—测试映射，不是任务状态库；旧映射保留，新测试按范围增补，不用新增测试数升级资格。

工作状态建议：`READY / IN_PROGRESS / BLOCKED / PARTIAL / DONE_SCOPED / DEFERRED`。
既有 DONE 等历史值保留原义；`DONE_SCOPED` 必须有报告和适用域。
试验结果另用 `PASS / FAIL / NOT_RUN / BLOCKED_DATA / NOT_VALIDATED`。
`READY` 不代表跑过；`PARTIAL` 不代表本轮正在实施；阻塞必须说明原因和解除条件。

## 4. 冲突处理

职责不是一条简单的文档覆盖链：

1. 已批准需求/ADR约束目标；代码不能自动修改它们。
2. BACKLOG 指定任务状态，当前计划指定执行顺序，SPEC 指定验收范围。
3. 当前实现的事实由源码及对应版本证据共同确定；旧报告的 PASS 不自动继承到新源码。
4. 计划与代码不一致时报告差距，不改参考数据“使两者一致”。
5. 未批准的新模型假设仅在明确标注的试验分支开展，不覆盖当前标准答案。

启动入口和根 README 不再内嵌“先做 B00/B01”等会过期的长提示，改为指向当前计划。

## 5. 每个任务必须同步哪些文档

| 变更类型 | 必须更新 | 不必无故修改 |
|---|---|---|
| 新票开始/阻塞/关闭 | BACKLOG；结束后报告；里程碑变化才更新 STATUS | ROADMAP 的目标与 r1 |
| 方程/参数语义/事件 | SPEC、原理、参数/词典（适用时）、架构（适用时）、测试映射和证据 | 原始 reference/ 与旧失败记录 |
| 接口/序列化/时钟 | SPEC、合同/架构、相关词典、跨平台测试与报告 | 生理真值定义，除非经批准 |
| 数值方法/边界 | SPEC、原理、声明域、各方法独立结果与报告 | 原输入、旧门槛和历史输出 |
| UI/导出器 | viewer 合同/使用/验收；相应软件测试 | 用改 UI 改物理数据 |
| 纯规划文档 | 索引、链接、依赖与范围自检 | 重新生成所有模型证据或宣称数值改善 |

## 6. 证据要求与审查

每份报告写：基线和结果源码身份、参数/初态/数据身份、实际命令/环境、结果和失败、
数值差异、与上一版的可比性、未覆盖项、可继续与需决策事项。格式见 [报告模板](tasks/REPORT_TEMPLATE.md)。
源码未提交时记录基线 commit + 工作区 diff 哈希；不能用未来 commit SHA 或“latest”伪造身份。

审查分别看“实现是否符合规则”和“是否满足任务意图”。任务完成至少要求两方面均有结论；
工具受限时如实记录，单人自审不称独立双代理审查。

## 7. 角色和提交范围

负责人批准用途、事件语义、结构性生理假设、验收及风险阈值；Codex 负责按票实施并更新事实。
同一文件的并行所有权在当前计划中预约。共享 `model.py/engine.py/contracts.py/units.py` 的修改分 PR 串行整合。
远端提交仅限 AGENTS.md 已授权的仓库；没有写权限不表示已发布。

## 9. 每轮维护与清理流程

1. 开始时核对分支、HEAD、未合并项和工作区，明确本任务文件责任；先读现有权威入口再新增文档。
2. 按第 5 节同步相应维护源。结果数字放原始记录/交付报告，能力摘要放 STATUS，入口保留链接。
3. 收口时检查相对链接、任务依赖、状态与报告对应；涉及证据清单或冻结路径时先查工具、manifest 和全仓引用。
4. 只删除本任务拥有、已由正式记录接管、没有活动引用或保留约束的临时稿/重复副本。修改时间久、名字像草稿或未跟踪都不能单独成为删除理由。
5. 在当次报告记录删除路径、理由和接管位置。原始输入需要保留时放本地导入区并核对哈希；其他人的未跟踪内容保持不动。
6. 纯文档更新检查链接、依赖、身份、diff 与提交范围，不重跑会覆盖原始结果的求解器；模型/接口/数值变更按对应任务完成实际验证。
7. 显式暂存本次文件清单；两轴审查后正常提交和推送授权分支。临时脚本、解压包、缓存及无关产物不混入文档提交。
